# Phase 3 dashboard contract

Build a responsive reception dashboard on the Phase 2 API. It must display only server data, never silently substitute demo records, and remain useful at desktop, tablet and narrow mobile widths.

## Session and trust boundary

The operator supplies a short-lived credential generated by the trusted CLI. Keep it only in JavaScript memory. Do not place it in URL, cookies, local/session storage, IndexedDB, logs, analytics or HTML. Refresh and sign-out clear it. Render all API text with DOM text properties, not HTML injection. Serve the dashboard and API from the same origin with a restrictive Content Security Policy.

## User flows

- Connect, verify identity, view role and clinic timezone, and sign out.
- View live totals and the current appointment/recall queues.
- View patients, appointments and recalls with explicit loading, empty and error states.
- Administrator/receptionist can add a patient, book an appointment, create a recall and apply valid status transitions.
- Optometrist sees the same operational data with write controls disabled and an explanation.
- Conflict, expiry, overlap, validation and dependency failures produce actionable messages; no optimistic success before the server confirms it.
- Local date/time input is converted using the browser offset and labelled clearly. The dashboard warns if the browser timezone differs from the clinic timezone; it does not silently resolve clinic DST ambiguity.

## Acceptance gates

- Keyboard navigation, focus visibility, semantic labels, live announcements, modal focus management and reduced-motion/high-contrast support.
- Automated browser tests against a real Node/PostgreSQL API cover connection, real data, patient creation, booking, recall, appointment transition, read-only role, invalid/expired credential, sign-out, conflict and narrow layout.
- Unit/API/PostgreSQL suites stay green. Container smoke confirms dashboard assets and API authentication.
- No third-party runtime asset, CDN, paid service, analytics, clinical workflow or external message delivery.
- Review in a separate PR; owner instruction is required to merge.
