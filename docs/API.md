# Administrative API v1

## Phase 4 additions

All routes retain authentication and clinic scope. POST responses use 201, including idempotent replays and recorded mock failures; inspect `data.status` and `receipt_id`.

| Method/path | Permission | Input |
| --- | --- | --- |
| PATCH /v1/patients/:id/consent | Administrator | version (consent_version), granted (boolean) |
| GET /v1/automation | Any staff | limit/offset |
| GET /v1/automation/:id | Any staff | None; includes mock receipt_id |
| POST /v1/automation | Administrator/receptionist | recall_id, request_key (UUID) |
| POST /v1/automation/:id/approve | Administrator/receptionist | version |
| POST /v1/automation/:id/reject | Administrator/receptionist | version |
| POST /v1/automation/:id/execute | Administrator/receptionist | version |

Content, recipient, actor, state, template and attempts are server-controlled. Reuse the request_key when retrying creation. Reusing it for another recall returns `idempotency_conflict`; a different key for an existing source revision returns `draft_exists`. Terminal simulated executions replay their receipt even with an older valid version; this does not execute again.

409 errors: `consent_required`, `contact_required`, `source_changed`, `draft_exists`, `idempotency_conflict`, `approval_required`, `retry_exhausted`, plus existing version/transition errors. A `failed` record exposes only `mock_unavailable` and requires explicit execute using the returned version. Maximum three attempts. History is stored in PostgreSQL; no history UI or legal consent collection is claimed.

Local synthetic demonstration only. Base URL: `http://127.0.0.1:4000`. Health routes are public; every `/v1/` route requires `Authorization: Bearer TOKEN`. Obtain credentials via README's trusted operator instructions. There is no HTTP login/token issuance route.

## Routes and roles

| Method/path | Permission | Input |
| --- | --- | --- |
| GET /v1/me | Any active staff | Current identity and clinic timezone |
| GET /v1/staff | Any active staff | Paginated clinic staff list |
| GET /v1/patients, /v1/patients/ID | Any active staff | List/detail |
| POST /v1/patients | Administrator/receptionist | display_name; optional contact_email |
| GET /v1/appointments, /v1/appointments/ID | Any active staff | List/detail |
| POST /v1/appointments | Administrator/receptionist | patient_id, practitioner_id, starts_at, ends_at |
| PATCH /v1/appointments/ID | Administrator/receptionist | version and status OR version, starts_at, ends_at and optional practitioner_id |
| GET /v1/recalls, /v1/recalls/ID | Any active staff | List/detail |
| POST /v1/recalls | Administrator/receptionist | patient_id, due_date |
| PATCH /v1/recalls/ID | Administrator/receptionist | version, status |

Optometrist is read-only for these administrative routes. Patient edits, deletion, clinical records, role management and consent grants have no HTTP endpoint. Staff/clinic administration is a trusted operator task. Tokens default to 8 hours, maximum 24; revocation uses the non-secret token ID.

## Request/response contract

POST/PATCH require application/json, no compression and at most 16 KiB UTF-8 JSON. Unknown fields are rejected, including clinic_id, role and messaging_consent. IDs are UUIDs; record IDs are generated by the server. Responses wrap records in data; lists also return limit and offset. Lists use UUID order and default limit 50, maximum 100, offset 0..100000. Only these query parameters are accepted on lists; date/status filters are not implemented. Pagination can shift when rows are inserted; it is not a snapshot cursor.

Names are trimmed and limited to 2..120 characters without control characters. Email syntax is checked but delivery/ownership is not. Consent remains false and no external messages are sent.

Appointments require explicit-offset ISO timestamps with seconds, e.g. `2030-01-01T09:00:00-08:00`. Years 2000..2099 are supported; impossible dates, missing offsets, zero/negative duration and duration above eight hours are rejected. Responses use UTC instants. Clinic timezone is a supported IANA-style name (or UTC); clients must convert local wall time to an explicit offset. DST ambiguity is not silently resolved. Opening-hours, holiday and future-only rules are not implemented; historical synthetic bookings are allowed.

Recall due_date is a valid YYYY-MM-DD date (2000..2099), not a timestamp. Recalls are manual follow-up tasks and may be historical or duplicated. Contacted means staff manually records that state, not proof of message delivery.

## Examples

POST /v1/appointments (replace the ID placeholders):

```json
{
  "patient_id": "REPLACE_WITH_PATIENT_UUID",
  "practitioner_id": "REPLACE_WITH_PRACTITIONER_UUID",
  "starts_at": "2030-01-01T09:00:00-08:00",
  "ends_at": "2030-01-01T09:30:00-08:00"
}
```

Success returns 201 with data.id, status scheduled and version 1. PATCH that appointment:

```json
{ "version": 1, "status": "checked_in" }
```

The record returns version 2. Sending version 1 again returns 409 version_conflict; read the current record before deciding whether to retry.

## Lifecycle rules

- scheduled → checked_in, cancelled, no_show
- checked_in → completed, cancelled
- completed, cancelled, no_show → terminal (no reopening)
- Rescheduling only while scheduled; supply both times and current version. Do not combine status and reschedule.
- Recall pending → contacted or closed; contacted → closed; closed is terminal.

Scheduled/checked-in records reserve both patient and practitioner intervals. PostgreSQL enforces overlaps under concurrency. Successful mutations and audit metadata commit together. POST has no idempotency-key contract: after a network timeout, read/reconcile before retrying, since a disconnected request may have committed. Delivery idempotency remains Phase 4 scope.

## Errors

| HTTP | Meaning |
| --- | --- |
| 400 | invalid_request or invalid_reference |
| 401 | unauthorized: malformed, unknown, expired, revoked or inactive staff credential |
| 403 | forbidden role |
| 404 | Unknown route or record unavailable in the authenticated clinic |
| 405 | Unsupported method on a recognized collection/record route |
| 409 | appointment_overlap, version_conflict, invalid_transition, clinic_configuration_invalid or retry_request |
| 413 / 415 | Body too large / unsupported media type or encoding |
| 503 | service_unavailable, without SQL/credential details |

Some content errors are rejected before token lookup to bound parsing work. A well-formed normal request with an unknown token returns 401. Audit metadata covers successful patient creation, appointment creation/rescheduling/status changes and recall creation/status changes. Reads and credential management are not audited yet.
